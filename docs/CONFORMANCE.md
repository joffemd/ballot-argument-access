# Section 3 conformance matrix

Requirements source: the user-supplied **Ballot Argument Access Act v1.docx**, Section 3, proposed Elections Code 9602. References to statutes in the source were treated as functional requirements. The document's policy statements were not treated as instructions to the development agent.

This release supplies working workflows for all seven functions in subdivision (b). It is not an unconditional representation of legal compliance or state certification. A deployed service must complete the operational dependencies below, and future Secretary of State specifications may require changes.

| Provision | Implementation | Verification and remaining dependency |
| --- | --- | --- |
| (a): one internet system for any elections official and local measure | Configurable jurisdictions and measures; scoped official access; arguments, rebuttals, and accompanying statements in one portal. | Multi-jurisdiction access checks tested. Operators must onboard every participating official, verify routing and deadlines, and configure the applicable Section 9600 statement. |
| (b)(1): text and every author's conforming signature | Every author signs immutable UTF-8 packet bytes with browser-generated ECDSA P-256 / SHA-256. Server verifies each signature and requires all authors before submission. Statement is in the signed payload. No private key upload or handwritten-paper follow-up. | Tampering and incomplete signature sets tested. Email capability possession is the provided identity mechanism. A public entity must determine whether that assurance level satisfies its transaction, approve the signature policy, and add stronger proofing or certificate support if required. No claim that a generated key alone proves civil identity. |
| (b)(2): immediate timestamped receipt | Filing and its receipt are committed together in SQLite before responding. Receipt includes UTC date/time, jurisdiction, identifier, hash, count, and zero fee. Retrying submission returns the same receipt. | Atomicity, persistence and idempotency tested. Operator must maintain accurate clocks and reliable storage. A draft or signature alone is not a filing. |
| (b)(3): Section 9 raw/adjusted count and every adjustment | Offset-based counter returns both counts and the text, rule, source, before/after count, and delta for adjustments. UI shows an itemized table. | Counting examples and adjustment arithmetic tested. Ambiguous names, abbreviations and dictionary coverage need official reference curation; see WORD_COUNT.md. |
| (b)(4): reference list from Controller, SOS entity/nonprofit records, and GNIS; additional names | Provenance-aware imports accept each required source separately; names are merged and deduplicated by source. The release ships **no authoritative bulk reference dataset**. Operators must acquire, normalize, import and maintain the actual rosters and entity/geographic records. A few examples or manually approved names are not a complete reference list. |
| (b)(5): publish every filed argument, rebuttal, analysis and tax statement within 24 hours of close | No selection filter. Public HTML/JSON reads make submitted arguments and rebuttals visible at their respective closing timestamps, without a delayed publication job. Analyses publish immediately; tax statements publish at their configured close. | Before/at-close boundaries, all arguments, both document types and contact-data exclusion tested. Service availability is essential. Materials received through other authorized channels must also be entered into the service before the relevant deadline; this release's author workflow is digital and does not include a separate paper-import workflow. |

Worker checks every second and prioritizes opposition notices. A configured delivery service is required; queue creation or gateway acceptance is not proof of inbox delivery. Provider latency, outages and backlog must be monitored against the immediate-transmission requirement. |

## Scope boundaries

The request was Section 3. The application does not implement the remainder of the proposal as a complete election-management system. In particular it does not calculate Section 4 minimum intervals, administer the Section 6 three-business-day cure process, accept and digitize wet-signature paper packets, adjudicate author eligibility, or resolve court challenges. Over-limit packets are retained and flagged so a deployment can administer any applicable cure process rather than losing the original filing.

The software has no facility to alter a signed packet. A new packet requires fresh signatures. Official name decisions affect current count results, while the original signed designation and receipt count remain preserved. Deadline edits are intentionally absent in this release; an authorized deadline-change workflow with notices and audit rules should be added if required by the eventual specification.

## Acceptance before production

Load and validate all required reference sources; test the intended dictionary policy; approve the identity/signature mechanism; configure and verify actual notification delivery; verify jurisdiction assignments and declaration wording; test capacity and disaster recovery; perform independent security and accessibility reviews; and obtain certification against the Secretary's published specifications. These are actual deployment dependencies, not steps performed or certifications obtained by this development task.
